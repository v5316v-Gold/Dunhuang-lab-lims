## 3. 关键指标实测

| 指标 | 目标 | 实测 | 结论 |
|---|---|---|---|
| **RTO**(恢复时间) | ≤ 4h | **~10 秒**(备份→恢复 31 表) | ✅ 远超目标 |
| **RPO**(数据丢失) | ≤ 1h | 备份策略每日全量 + WAL;演练数据为备份时刻一致性 | ✅ 达标 |
| 备份完整性 | 100% | pg_restore -l 校验 + 表数/审计数核对 | ✅ |

## 4. 恢复流程要点(固化)

```
1. docker ps 确认容器可用
2. bash scripts/ops/backup.sh      # 确认最近备份存在(backups/)
3. bash scripts/ops/restore.sh backups/dunhuang_lims-<最新>.dump <目标库>
4. 验证: SELECT count(*) FROM audit_logs(应 ≥ 备份时数量)
5. 应用 DATABASE_URL 指向恢复库,重启 backend
6. /health/deep 确认 postgres/audit up
7. 记录演练报告
```

## 5. 发现与改进

| 发现 | 级别 | 处理 |
|---|---|---|
| Windows git-bash 二进制管道破坏 dump | 中 | backup.sh 已改为容器内生成 + docker cp(Phase 1 已修复) |
| 恢复需手动指定库名 | 低 | restore.sh 默认恢复临时库,生产需 FORCE_RESTORE=1 显式确认 |
| 生产主备架构未落地 | 中 | Phase 5 前评估 PostgreSQL Operator/Patroni |

## 6. 演练结论

**DR-2026-01 PASS**: 备份→校验→恢复→验证全链路实测通过,RTO 实测 ~10 秒(目标 4h),恢复后数据完整。
