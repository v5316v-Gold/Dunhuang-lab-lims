## 0. 执行方案总览

### 0.1 任务定义

按既定层级**逐层编写设计规范,不得调整层级、不得跳层、不得合并**:

```
L0 项目架构 → L0.5 领域架构 → L1 业务架构 → L2 合规架构 → L3 数据架构
→ L4 应用架构 → L5 技术架构 → L6 基础设施架构 → L7 验证架构 → L8 运维架构
```

**共 10 层**(含 L0.5)。每一层产出**一份独立规范文档**,统一采用 20 字段模板。严格执行 **L0 → L8 顺序**,每层验收通过后方可进入下一层。

### 0.2 关键原则

| # | 原则 | 说明 |
|---|---|---|
| P1 | **严格顺序** | L0 → L0.5 → L1 → … → L8,禁止跳层/并行/倒序 |
| P2 | **统一模板** | 每层 20 字段模板,字段不可省略(不适用的标 N/A) |
| P3 | **单层单文档** | 每层一份 md 文档,存于 `docs/architecture/` |
| P4 | **层间追溯** | 每层输出 → 下一层输入;文档头部记录来源与去向 |
| P5 | **Gate 验收** | 每层完成后过验收检查表(§7),未过不得进入下一层 |
| P6 | **合规贯穿** | 每层都需回答"本层如何支撑 CNAS-CL01:2018 条款" |
| P7 | **版本与变更** | 每层文档纳入 git;修改走变更控制 |
| P8 | **规模控制** | 每层 300-800 行;超长拆分附录 |

## 1. 统一输出模板规范(20 字段)

> 每层文档必须按此模板顺序书写。模板详情见 `TEMPLATE.md`。

| # | 字段 | 定义 | 填写要求 |
|---|---|---|---|
| 1 | **节点名称** | 本层唯一标识 | 如 `L3-数据架构(Data Architecture)` |
| 2 | **建设目标** | 本层要达成的结果(可验证) | 用动词开头,3-5 条 |
| 3 | **业务范围** | 本层覆盖的业务/技术边界 | 明确 in-scope / out-of-scope |
| 4 | **背景** | 为什么需要本层、现状与痛点 | 引用依据(标准/ADR/审计发现) |
| 5 | **参与角色** | 本层编写/评审/批准角色 | RACI 或角色表 |
| 6 | **输入 - 输出** | 本层消费的上层产物、产出的下层产物 | 表格:来源层 → 本层 → 去向层 |
| 7 | **前置后置条件** | 进入本层必须满足 / 离开本层必须满足 | 可验证条件 |
| 8 | **业务流程** | 本层视角下的流程(文字+流向描述) | 节点 → 流向,不假装看图 |
| 9 | **状态机** | 本层关键对象的状态流转 | 状态表 + 转换事件 + 守卫条件 |
| 10 | **数据模型** | 本层涉及的数据实体与关系 | 实体清单 + 关系 |
| 11 | **字段** | 关键字段定义 | 字段名/类型/必填/默认/约束 |
| 12 | **业务规则** | 本层强制规则(不可绕过) | 编号 BR-xx,可测试 |
| 13 | **异常处理** | 失败场景与响应 | 异常清单 + 处理策略 |
| 14 | **RBAC 要求** | 本层的权限矩阵 | 角色 × 操作矩阵 |
| 15 | **审计要求** | 本层需记录的审计事件 | 事件清单 + 字段 |
| 16 | **合规要求 (CNAS/CMA/ISO 17025)** | 本层支撑的条款 | `标准号 + 条款号`,如 CNAS-CL01:2018 §7.5 |
| 17 | **API 要求(如适用)** | 本层暴露/消费的接口 | 接口契约,不适用标 N/A |
| 18 | **验收标准** | 本层 Gate 通过条件 | 可测试/可检查清单 |
| 19 | **依赖关系** | 本层依赖与提供给下层的 | 上游依赖 + 下游供应 |
| 20 | **附录** | 补充材料/变更记录 | 版本历史 + 参考资料 |

## 3. 逐层执行方案

> 每层均按 §4 执行节奏:起草 → 自检 → 评审 → 验收 → 归档 → 下一层。

### 3.1 L0 — 项目架构 (Project Architecture)

| 维度 | 内容 |
|---|---|
| **节点名称** | L0-项目架构 |
| **建设目标** | ① 定义项目章程(定位/目标/边界);② 干系人与 RACI;③ 顶层 WBS 与里程碑;④ 项目级风险登记册;⑤ 治理与决策机制 |
| **业务范围** | 项目级治理(不涉及具体业务模块设计);In-scope:章程/范围/时间/预算/干系人;Out-of-scope:业务流程细节(属 L1) |
| **背景** | Phase 0 + 0.5 已完成,系统可运行;需在项目层面固化"为什么做、谁负责、做到什么程度" |
| **参与角色** | 决策层(菩提老祖)、LIMS 架构师(编写)、QA Manager(评审)、实验室主任(批准) |
| **输入-输出** | 输入:`PROJECT-STATUS.md`、`PHASE-0.5-RESULT.md`、`00-PROJECT-PLAN.md`;输出:章程(本层文档)供 L0.5 |
| **前置后置** | 前置:Phase 0.5 GATE PASS;后置:章程评审通过、里程碑定义完成 |
| **业务流程** | 立项 → 范围定义 → 计划(WBS) → 执行 → 监控 → 收尾;本层固化前 3 步 |
| **状态机** | 项目生命周期:INITIATING → PLANNING → EXECUTING → MONITORING → CLOSING |
| **数据模型** | 项目实体:干系人/里程碑/风险/预算/范围项 |
| **字段** | 项目名/版本/目标/范围(含 out-of-scope)/时间线/预算/负责人 |
| **业务规则** | BR-L0-01 范围变更须经管理评审;BR-L0-02 里程碑延期 > 1 周须上报 |
| **异常处理** | 范围蔓延 → 变更控制;资源不足 → 风险升级;预算超支 → 管理评审 |
| **RBAC** | 项目文档:决策层可批、架构师可写、QA 可读;Git 分支保护:main 仅 PR 合入 |
| **审计要求** | 项目决策记录(ADR 索引)、里程碑评审记录 |
| **合规要求** | CNAS-CL01:2018 §5.1(组织)、§8.9(管理评审) |
| **API 要求** | N/A |
| **验收标准** | □ 章程定稿并签字 □ 干系人 RACI 完整 □ 里程碑可追踪 □ 风险登记册含 Top10 □ Gate 记录归档 |
| **依赖关系** | 上游:无(第一层);下游:为 L0.5 提供边界与术语 |

### 3.2 L0.5 — 领域架构 (Domain Architecture)

| 维度 | 内容 |
|---|---|
| **节点名称** | L0.5-领域架构 |
| **建设目标** | ① 识别领域与限界上下文(DDD);② 定义聚合根与领域事件;③ 领域术语表;④ 领域规则沉淀 |
| **业务范围** | 贵金属检测全业务域;In-scope:样品/批次/检测/质控/报告/设备/人员/试剂/EHS/客户服务;Out-of-scope:技术实现(属 L5) |
| **背景** | 业务复杂(火试金+ICP 双流程),需先建模避免技术绑架业务(参考 ADR-0011) |
| **参与角色** | 领域专家(实验室主任/资深检测员)、LIMS 架构师(编写)、QA Manager(评审) |
| **输入-输出** | 输入:L0 章程 + 业务访谈;输出:领域地图供 L1 |
| **前置后置** | 前置:L0 GATE PASS;后置:限界上下文清单评审通过 |
| **业务流程** | 上下文映射:委托→接收→检测执行→质控→报告→归档(每上下文内部流程归 L1) |
| **状态机** | 聚合级状态:Sample(Batch 流程见 L4 细化);领域事件:SampleReceived / BatchCreated / TestCompleted / ReportApproved |
| **数据模型** | 聚合根:Sample / SampleBatch / Test / Report / Equipment / Reagent;每个聚合的实体清单 |
| **字段** | 聚合 ID/版本号(乐观锁)/时间戳;业务字段归 L3 细化 |
| **业务规则** | BR-D-01 火试金必须 ≥2 平行样;BR-D-02 报告签发前必须 QC 通过;BR-D-03 样品唯一性编号规则 |
| **异常处理** | 领域冲突 → 领域事件补偿;并发修改 → 乐观锁冲突重试 |
| **RBAC** | 领域级角色命名:检测员/审核员/授权签字人/质量经理/设备管理员 |
| **审计要求** | 领域事件可追溯(为 L2 审计链提供事件源) |
| **合规要求** | CNAS-CL01:2018 §7 全条款在领域地图上的映射 |
| **API 要求** | N/A(领域事件清单,API 归 L4) |
| **验收标准** | □ 领域地图评审通过 □ 聚合清单完整 □ 术语表 ≥ 50 词 □ 领域规则 ≥ 10 条 |
| **依赖关系** | 上游:L0;下游:L1 业务流程 + L3 数据模型依据 |

### 3.4 L2 — 合规架构 (Compliance Architecture)

| 维度 | 内容 |
|---|---|
| **节点名称** | L2-合规架构 |
| **建设目标** | ① CNAS/CMA/ISO 17025 条款 → 系统功能映射矩阵;② ALCOA+ 九原则实现方案;③ 电子签名/审计追踪/权限分离设计;④ 数据完整性红线 |
| **业务范围** | 合规机制全系统(审计链/电子签名/RBAC/数据保留/防篡改) |
| **背景** | 现有:27 trigger 审计链 + 3 防篡改 + 软删除 + JWT/MFA;需固化为架构规范 |
| **参与角色** | 合规顾问、QA Manager、LIMS 架构师(编写)、实验室主任(批准) |
| **输入-输出** | 输入:L1 流程 + 04-CNAS-COMPLIANCE.md + validation/FMEA;输出:合规矩阵供 L3-L7 |
| **前置后置** | 前置:L1 GATE PASS;后置:条款映射 100% 覆盖 |
| **业务流程** | 法规解读→条款映射→差距分析→实现方案→验证证据链 |
| **状态机** | 合规项生命周期:IDENTIFIED → MAPPED → IMPLEMENTED → VERIFIED → MONITORED |
| **数据模型** | 合规项/条款/证据/风险(链接 FMEA) |
| **字段** | 条款号/要求描述/实现位置/证据文件/状态 |
| **业务规则** | BR-C-01 审计日志不可改(append-only);BR-C-02 电子签名 = 双因素;BR-C-03 数据保留 ≥ 5 年 |
| **异常处理** | 断链告警/越权尝试/签名失败 |
| **RBAC** | 职责分离:检测员≠审核员≠签发人;管理员不可改审计数据 |
| **审计要求** | 审计追踪:登录/增删改/权限变更/配置变更(4 类事件) |
| **合规要求** | CNAS-CL01:2018 全条款 + ALCOA+ + 21 CFR Part 11 §11.10/§11.50/§11.70/§11.100 |
| **API 要求** | 审计查询/verify 端点(已有) |
| **验收标准** | □ 条款矩阵 100% 覆盖 □ ALCOA+ 9 项各有关联实现 □ 电子签名规格定稿 □ 审计事件 4 类定义完整 |
| **依赖关系** | 上游:L1;下游:L3 数据保留、L4 RBAC 实现、L7 验证证据 |

## 4. 执行节奏(Gate 流程)

### 4.1 每层执行步骤(6 步)

```
┌─ 1. 起草 ──────────── 按 20 字段模板撰写初稿
├─ 2. 自检 ──────────── 对照本层验收标准自检(检查表 §7)
├─ 3. 评审 ──────────── 相关角色评审(见每层"参与角色")
├─ 4. 修订 ──────────── 按评审意见修订
├─ 5. 验收 ──────────── Gate 检查表全 PASS + 记录归档(review/Lx-review.md)
└─ 6. 进入下一层 ────── 未过 Gate 禁止进入
```

### 4.2 Gate 检查表(通用)

| # | 检查项 |
|---|---|
| G1 | 20 字段模板全部填写(不适用的标 N/A) |
| G2 | 合规条款引用规范(标准号+条款号+发布年) |
| G3 | 与上层文档追溯一致(输入输出闭环) |
| G4 | 状态机/数据模型/规则可测试 |
| G5 | RBAC/审计/异常三件套齐全 |
| G6 | 验收标准可验证(非空话) |
| G7 | 评审记录与修订记录归档 |
| G8 | 文件纳入 git 并 commit(规范 commit message) |

### 4.3 总时间线(估算)

| 层 | 周期(人日) | 关键评审 |
|---|---|---|
| L0 | 0.5 | 决策层批准 |

## 5. 质量要求

1. **引用规范**:标准引用必带 `标准号 + 条款号 + 发布年`(如 `CNAS-CL01:2018 §7.5.1`)
2. **推断标注**:推断内容标 `[推]`,存疑标 `[存疑]`,不创造事实
3. **版本号**:技术选型必带版本(如 `NestJS 10.4 + Prisma 5.22`)
4. **文字描述流程**:不假装"看图",用节点→流向文字
5. **规模**:每层 300-800 行,附录可扩展
6. **模板一致性**:与 TEMPLATE.md 完全一致,可自动校验(脚本可选)

## 6. 风险与注意事项

| 风险 | 缓解 |
|---|---|
| 层间职责混淆(如 L2 合规 vs L7 验证) | 明确边界:L2 定义"做什么才合规",L7 定义"如何证明合规" |
| 与既有文档重复 | 分层文档引用既有文档,不复制;既有文档为输入 |
| 模板僵化(某些层不适用的字段) | 允许 N/A 但必须说明理由 |
| 规模失控 | 每层 800 行上限,超长拆附录 |
| 评审流于形式 | Gate 检查表 G1-G8 强制 + 验收记录留痕 |
| 文档漂移(写归写、做归做) | 每层验收绑定代码/配置现状核对(如 L3 对齐 schema.prisma) |

```
L0 项目架构 (草案→评审→Gate) 
  → L0.5 领域架构
  → L1 业务架构
```
